# Portfolio purpose and content policy

## Positioning

Pedro Henrique da Cruz Santos is a **Desenvolvedor Full Stack**. The portfolio should help recruiters and technical evaluators quickly understand his frontend strength and practical work with web products, APIs, integrations, automation, data, Docker, and pragmatic architecture.

The portfolio should show evidence, not a generic technology inventory. It serves Portuguese-speaking visitors first; an English version is a future product decision.

## Audiences and conversion

1. Recruiters should find the role, areas of strength, selected work, CV, and contact route quickly.
2. Technical reviewers should be able to inspect code and understand scope, architectural decisions, and constraints.
3. Potential clients should understand the kinds of product and operational problems Pedro can help solve.

## Factual-content policy

- Claims need a known source: Pedro's confirmation, project repository, validated artifact, or public deliverable.
- Do not infer impact from a technology choice. Metrics, client names, responsibilities, dates, and production status require confirmation.
- Write `UNKNOWN` in planning material for facts that still need confirmation. Do not publish `UNKNOWN` as visitor-facing content.
- Respect confidentiality. Prefer a generalized description when a client, system name, or operational detail cannot be published.

## Case-study record

Before publishing or materially revising a project, collect:

| Field | Required |
| --- | --- |
| Name, period, status, category | Yes |
| Context and problem | Yes |
| Pedro's responsibility | Yes |
| Architecture and technical decisions | Yes |
| Integrations, constraints, and challenges | When applicable |
| Technologies and their purpose | Yes |
| Result or learning | Yes, only when factual |
| Code, demo, screenshots, and confidentiality notes | When available |

Visitor-facing narrative follows: **context → problem → responsibility → decisions → solution → result/learning**.
